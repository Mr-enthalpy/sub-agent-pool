# Local Agent Scheduler V0.1 Implementation Specification

Status: frozen for V0.1 implementation; V0.1.2 correctness closure applied

Derived from: `ARCHITECTURE.md`

Scope: single scheduler process, single SQLite database, local execution targets

This specification narrows the architecture direction into implementable,
testable contracts. If it conflicts with a Core Invariant in `ARCHITECTURE.md`,
the invariant wins and the conflict must be reviewed explicitly.

## 1. Authority and execution model

SQLite is authoritative for Scheduler state. Physical processes, Codex threads,
adapter messages, and Root notifications are observations or delivery mechanics.
Execution is at-least-once. A current active lease with a matching fencing epoch
is required for every authoritative mutation produced by an Attempt.

V0.1 enforces one active Task per LogicalAgent. A Task has at most one current
lease. Old executions may finish, but their stale epoch cannot complete a Task,
promote a checkpoint, or replace LogicalAgent continuity.

## 2. State machines

### Task

| From | Operation | To |
|---|---|---|
| BLOCKED | all dependencies completed | QUEUED |
| QUEUED | transactional claim | LEASED |
| LEASED | execution start confirmed | RUNNING |
| LEASED/RUNNING | retryable NACK | RETRY_WAIT |
| RETRY_WAIT | retry eligibility reached | QUEUED |
| LEASED/RUNNING/RETRY_WAIT | policy exhausted or ambiguity | SUSPENDED |
| LEASED/RUNNING | valid success ACK | COMPLETED |
| BLOCKED/QUEUED/LEASED/RUNNING/RETRY_WAIT/SUSPENDED | cancel | CANCELLED |

`COMPLETED` and `CANCELLED` are terminal. Completed work is superseded by a new
Task; it is never reopened.

### Attempt

| From | Operation | To |
|---|---|---|
| ACTIVE | valid success ACK | SUCCEEDED |
| ACTIVE | NACK/start failure | FAILED |
| ACTIVE | lease expiry | EXPIRED |
| ACTIVE | cancellation | CANCELLED |

Every claim creates a new Attempt, even if no Execution is ever created.

### Lease

| From | Operation | To |
|---|---|---|
| ACTIVE | success/failure release | RELEASED |
| ACTIVE | deadline passes | EXPIRED |
| ACTIVE | cancellation/suspension | REVOKED |

The fencing epoch is monotonically increasing per Task.

### Execution

| From | Operation | To |
|---|---|---|
| STARTING | adapter confirms start | RUNNING |
| STARTING | adapter rejects start | FAILED |
| STARTING | start outcome ambiguous | UNKNOWN |
| RUNNING | standardized success | SUCCEEDED |
| RUNNING | standardized failure | FAILED |
| RUNNING | lost during observation | LOST |
| STARTING/RUNNING/UNKNOWN | confirmed termination | TERMINATED |

An Execution state never directly mutates Task authority without a current
Attempt/Lease check.

### LogicalAgent

| From | Operation | To |
|---|---|---|
| INITIALIZING | birth ready | READY |
| READY | claim assignment | ASSIGNED |
| ASSIGNED | task boundary | READY or RETIRED |
| READY/ASSIGNED | physical loss requiring continuity | REVIVING |
| REVIVING | replacement incarnation ready | READY or ASSIGNED |
| ASSIGNED | topology drain | DRAINING |
| DRAINING | assignment boundary | RETIRED |
| non-RETIRED | policy/manual suspension | SUSPENDED |

RETIRED is terminal and cannot revive. Committing semantic retirement fences
every STARTING/WARM/COLD Incarnation as LOST so a reusable physical presence is
never left scheduler-authoritative after its LogicalAgent dies semantically.

### Batch

| From | Operation | To |
|---|---|---|
| OPEN | submission committed | ACTIVE |
| ACTIVE | all Tasks completed | COMPLETED |
| ACTIVE | any Task suspended | SUSPENDED |
| OPEN/ACTIVE/SUSPENDED | cancel | CANCELLED |
| SUSPENDED | Root recovery operation | ACTIVE |

Batch completion depends on Task completion and durable Result creation, not
Root Result acknowledgement.

V0.1 has no optional Task path. Every submitted Task participates in the Batch
barrier and produces its authoritative Result before normal Batch completion.

## 3. Transaction boundaries

The following operations are single SQLite transactions:

1. Batch + Task graph + dependency insertion and initial BLOCKED/QUEUED states.
2. Task claim + fencing epoch increment + Attempt + Lease + LogicalAgent ASSIGNED.
3. Execution record creation associated with an Attempt and Incarnation.
4. Valid success ACK: Attempt SUCCEEDED, Lease RELEASED, Task COMPLETED, exactly
   one Result AVAILABLE, dependency release, and Batch recomputation. Root wakeup
   is emitted only at the Batch/control boundary.
5. Retryable NACK: Failure record, Attempt FAILED, Lease RELEASED, Task
   RETRY_WAIT with eligibility timestamp, LogicalAgent release.
6. Suspend: Task SUSPENDED, current Lease REVOKED, open Escalation, Batch
   SUSPENDED, and durable decision-required outbox event.
7. Root Result ACK changes only Result state.
8. Checkpoint promotion requires matching active Attempt and lease epoch.
9. Topology revision and desired partition mutations are atomic.

## 4. Schema constraints and fencing

IDs are UUID strings. Times are UTC epoch seconds. JSON payloads are canonical
JSON text. Foreign keys are enabled. WAL and `synchronous=FULL` are required.

Partial unique indexes enforce:

* one ACTIVE lease per Task;
* one ACTIVE Attempt per Task;
* one ACTIVE Attempt per LogicalAgent;
* one Execution history row per Attempt;
* one authoritative Result per Task;
* one open Escalation per suspended Task;
* one assigned LogicalAgent per Task;
* one STARTING/WARM/COLD Incarnation per LogicalAgent;
* at most one STARTING/RUNNING/UNKNOWN Execution per Incarnation.

Every Attempt stores its lease epoch. Success, NACK, heartbeat, and checkpoint
promotion require `task.current_attempt_id`, `lease.state=ACTIVE`, and matching
epoch. Authority validation also rejects a lease at or beyond `expires_at`, even
if the expiry sweep has not yet updated its row. A stale outcome is recorded on
Execution history only.

## 5. Matching and pool reconciliation

Eligible matching order is deterministic:

1. exact partition;
2. required workstream continuity, otherwise reject;
3. preferred workstream continuity before no prior affinity;
4. required affinity tags as a subset of agent tags;
5. READY agents before cold/revivable agents;
6. oldest `available_since`, then LogicalAgent ID.

Each PoolPartition stores desired resident capacity and retention policy.
`partition_name` is current membership; `pending_partition_name`, when present,
is desired membership. Reconciliation counts an assigned pending inbound member
against its desired partition, while excluding SUSPENDED identities and
retirement drains from schedulable capacity. `MOVE_CAPACITY` may still select a
SUSPENDED identity to change its desired membership without claiming that it is
available capacity. Reconciliation may birth a temporary schedulable replacement;
after the safety obligation is resolved and the suspended identity reaches its
destination, deterministic excess reconciliation retires the replacement rather
than the preserved identity. Excess unassigned READY/INITIALIZING/REVIVING members retire directly.
Only ASSIGNED members need to enter DRAINING and apply a pending transition at
their assignment boundary.
`MOVE_CAPACITY` selects from the same population: unassigned
INITIALIZING/READY/REVIVING identities cut over immediately and preserve their
state and identity; ASSIGNED identities record the desired partition and drain.

An idle READY identity has no assignment boundary. When MOVE or MERGE crosses
ExecutionTarget and the identity has a reusable STARTING/WARM/COLD Incarnation
but no active Attempt or Execution, the topology transaction fences that old
binding as LOST and moves the same LogicalAgent immediately. It must not leave
an unassigned DRAINING identity or birth a replacement merely because the
pending transition cannot complete.

An authority-ended Execution may remain STARTING/RUNNING/UNKNOWN so its late
physical outcome remains reconcilable. That stale-history state does not block
logical membership cutover when the expired Attempt was read-only, its frozen
Execution snapshot proves attempt isolation, or physical quiescence is
confirmed. A non-isolated writer with unknown quiescence remains SUSPENDED with
only desired membership pending until the safety obligation is resolved.
This predicate is evaluated by the cutover primitive itself, so expiry before
MOVE/MERGE and MOVE/MERGE before expiry converge to the same membership result.

MOVE preserves identity and continuity. The normal Root-facing surface moves
declared capacity; direct `move-agent` remains a diagnostic/admin primitive.
MERGE atomically adds the two declared desired capacities, migrates source
LogicalAgents, and changes every nonterminal source Task's future scheduling
classification to the target before retiring the source partition. An already
active Attempt keeps its frozen LogicalAgent, ExecutionTarget/Profile, and lease
epoch; a later retry uses the migrated Task partition. MERGE also rebases every
pending inbound reference to its canonical target and never overwrites an
already-different desired partition. RETIRE is rejected while any nonterminal
Task or inbound desired LogicalAgent remains in the partition. At immediate or
assignment-boundary cutover, the LogicalAgent atomically adopts the target
partition's retention policy. MERGE never combines private continuity.

`pool upsert` creates a partition or idempotently re-declares the exact existing
definition. In V0.1, an existing partition's retention, ExecutionTarget,
ExecutionProfile, and tags are immutable, and capacity changes use `resize`.
An inactive partition cannot be reactivated by upsert. The CLI rejects targets
or profiles absent from current configuration; runtime treats unavailable
execution configuration as `RESOURCE_UNAVAILABLE` rather than allowing a
`KeyError` to escape the dispatcher loop.

## 6. Birth, incarnation, revival, and continuity

Birth allocates a new LogicalAgent ID and generation zero continuity. Revival
restores logical availability for an existing non-RETIRED LogicalAgent and its
latest committed bounded continuity capsule. READY does not imply physical
presence. An Incarnation is created or reused only when dispatch requests a
physical execution. It binds to one ExecutionTarget; LogicalAgent does not.

V0.1.2 freezes `Incarnation` as one physical embodiment, not an Execution
wrapper. A genuinely resident physical Incarnation may host sequential
Executions, but never more than one active Execution. The current Codex adapter
creates and closes a fresh app-server session/thread for each Execution, so its
Executions still receive distinct Incarnation generations. `STARTING`, `WARM`,
and `COLD` denote potentially live physical presence. A confirmed closed
physical presence becomes `TERMINATED`; lost or unconfirmed presence is fenced
as `LOST`.
A late stale outcome may refine its own old Incarnation from `LOST` to
`TERMINATED`, but cannot alter Task, Result, checkpoint, or replacement
Incarnation authority. `COLD` is reserved for a future safely detachable
physical presence and is treated as active even though V0.1.2 creates none.
Late start/reconciliation observations also durably preserve every newly known
runtime locator on the exact Execution and Incarnation. RUNNING, ambiguous, and
terminal late starts use this physical-only path; none may regain Task/Lease
authority or escape the dispatcher merely because authority ended meanwhile.

Continuity capsules are JSON objects limited by configuration byte size and the
fixed keys listed in the architecture direction. Unknown keys are rejected.
Promotion increments a continuity version and is fenced by current Attempt.

## 7. Writer recovery

Tasks declare `workspace_mode` as `read_only` or `write`. Lease expiry does not
prove a writer stopped. Replacement dispatch for a write Task is permitted only
when the previous Execution is confirmed terminal/quiescent or that Execution's
durable creation-time safety snapshot records attempt isolation. The snapshot
is frozen before physical start and is never recomputed from current target
configuration after restart. Otherwise recovery atomically suspends the Task and
creates an Escalation with `WRITER_QUIESCENCE_UNKNOWN`. The affected
LogicalAgent also remains SUSPENDED and cannot accept unrelated work while its
old physical writer may still be active. Confirmed quiescence/isolation moves
the identity through REVIVING before it becomes assignable again.

Cancellation revokes Scheduler authority but is not itself proof that a
physical writer stopped. Cancelling an active writer with unknown quiescence
keeps its LogicalAgent SUSPENDED and emits an Escalation. The explicit
`release_cancelled_writer` recovery primitive requires confirmed quiescence or
the same frozen Execution isolation fact before revival.

When that safety obligation is resolved, any desired partition transition is
committed before the LogicalAgent can become schedulable: resolve the canonical
MERGE target, adopt its retention policy, fence obsolete physical presence, and
clear `pending_partition_name`. Resident identities then pass through REVIVING;
an ephemeral destination retires the same identity instead of reviving it.

Replacement prompts state that current workspace state is authoritative and
require inspection of assignment-scoped state before idempotent continuation.

## 8. Retry and failure classification

Adapters produce standardized classes: `TRANSIENT_EXTERNAL`, `TIMEOUT`,
`EXECUTION_LOST`, `START_FAILURE`, `RESOURCE_UNAVAILABLE`, `PERMISSION_FAILURE`,
`INVALID_RESULT`, `ADAPTER_PROTOCOL_FAILURE`, and `UNKNOWN`.

Only classes named in a Task's retry policy may be retried. Backoff is
deterministic exponential delay capped by configuration. Exhausted or
unclassified failure suspends and escalates. The Scheduler never changes model,
role, affinity, or acceptance semantics on its own.

## 9. ExecutionAdapter contract

The narrow interface is:

* `start_execution(request) -> StartObservation`
* `observe_execution(handle) -> ExecutionObservation`
* `interrupt_execution(handle) -> ExecutionObservation`
* `terminate_execution(handle) -> ExecutionObservation`
* `collect_outcome(handle) -> ExecutionOutcome`
* `reconcile_start(request_id, persisted_runtime_handle) -> StartObservation`

These are synchronous Scheduler-facing calls and every call must return within
the adapter's configured operation deadline. The adapter owns bounded process,
transport, and stream I/O and translates deadline expiry into the existing
timeout, ambiguous-start, observation, or outcome vocabulary. V0.1 does not
provide a generic adapter watchdog; an implementation that can block forever
violates the ExecutionAdapter contract.

After each successful external start stage, an adapter captures every locator it
has just received before checking whether enough budget remains for the next
stage. A timeout therefore returns the complete identity earned so far. If
adapter/session construction fails after creating a child process, construction
must terminate or otherwise abandon that process deterministically. The shipped
Codex adapter bounds its post-spawn initialization and request I/O; Python's
platform `Popen` call itself remains a narrow platform limitation rather than a
Scheduler authority primitive.

The shipped Codex adapter establishes one absolute deadline for each
Scheduler-facing method. In `start_execution`, session initialization,
`thread/start`, and `turn/start` consume the same remaining budget rather than
receiving fresh timeouts. Within each JSONL request, `stdin.write`, `flush`, and
response wait also share that remaining deadline. If write or response progress
exceeds it, the session process is forcibly abandoned so pipe backpressure
cannot permanently block Scheduler supervision.

The Codex adapter uses `codex app-server` over stdio JSONL. Codex thread IDs and
turn IDs are opaque runtime handles stored only on Incarnation/Execution rows.
Recovery uses `thread/read(includeTurns=true)` and reconciles the exact persisted
turn ID; an ambiguous start may use the sole turn in the dedicated V0.1 thread,
but never guesses among multiple turns. Physical session reuse is not
implemented. If a future adapter adds it, an Incarnation may span multiple
turns only while that same physical embodiment remains alive; it must not span
newly created sessions. Correctness does not depend on a permanently live
app-server process.

Codex sandbox configuration is a maximum permission ceiling. Every read-only
Task is dispatched with the actual `read-only` sandbox; write Tasks use
`workspace-write` only when the configured ceiling permits it. Configuration is
strictly one of `read-only`, `workspace-write`,
or `danger-full-access`, matching the current app-server protocol. A persisted
turn with status `interrupted` is an `EXECUTION_LOST` observation, not an
adapter-protocol failure.

## 10. RootBridge contract

`deliver(event_id, event_type, payload) -> DeliveryObservation` is independent
of worker execution. Events remain in `notification_outbox` until delivered and
acknowledged according to at-least-once policy. RootBridge failure never changes
Task, Result, or Batch state. Each implementation must bound a delivery call.
The daemon's dedicated notifier thread performs only outbox delivery and
delivery/backoff state updates; it cannot supervise Tasks, renew Leases,
recompute Batches, or consume Results. Slow notification I/O therefore cannot
block the dispatcher or heartbeat control loops. Delivery success timestamps
and retry eligibility are calculated from the completion of the bounded bridge
call, not its start, so a slow failure still receives its declared backoff.
Each `SchedulerDaemon` object owns exactly one run lifecycle. A second `run()`
or `run_until_idle()` call is rejected; callers construct a new daemon rather
than racing a notifier thread still completing bounded shutdown.

V0.1 includes two RootBridge implementations. The filesystem bridge atomically
publishes minimal event envelopes into a configured inbox. The Codex app-server
bridge resumes a configured Root thread, starts a notification turn, and marks
delivery only after the matching turn completes. Live `turn/completed` is the
preferred evidence; if that notification is lost, the bridge reconciles the
exact turn ID against persisted `thread/read` state. This is transport-internal
reconciliation, not Root polling: Root remains dormant until a wakeup arrives.
Both are wakeup/control
transport only; they include event IDs and entity indexes, while the CLI/SQLite
Result Queue remains the data source. `RESULT_AVAILABLE` is durable Result state,
not a per-Task Root wakeup. Normal wakeup occurs once through
`BATCH_RESULTS_READY`; suspension and decision events remain control wakeups.

## 11. Startup reconciliation

Startup enters RECOVERY before dispatch:

1. enter RECOVERY and identify/expire overdue authority plus ACTIVE claims that
   never created an Execution, before either can heartbeat or ACK;
2. apply deterministic read-only retry policy and suspend writers whose
   quiescence is unknown;
3. ask the owning adapter to reconcile still-authoritative or stale-unresolved
   STARTING/UNKNOWN/RUNNING handles by persisted execution identity; an active
   Execution whose adapter is unavailable loses Task authority according to the
   normal failure policy but remains physical state `UNKNOWN` while termination
   and quiescence are unconfirmed, so a restored adapter can reconcile it and an
   unsafe writer still blocks topology cutover; adapter presence alone does not
   admit Lease renewal;
   the current daemon must positively observe the exact Execution as RUNNING;
4. record confirmed terminal outcomes, fencing any stale completion to
   Execution history only;
5. promote eligible retry waits;
6. reconcile pool capacity and revive eligible LogicalAgents without reviving
   RETIRED identities;
7. drain pending topology changes at safe boundaries;
8. mark Scheduler READY and begin normal dispatch.

Schema migration precedes RECOVERY. A pre-closure MERGE revision without both
declared-capacity snapshots, or any nonterminal Task stranded on an inactive
partition, is ambiguous historical topology. Migration fails atomically with
`LEGACY_TOPOLOGY_REPAIR_REQUIRED`; it does not infer capacity from runtime
population or silently move Tasks. The operator must preserve the database and
perform an audited offline repair before Scheduler startup can continue.

Heartbeat/notifier startup and the remaining recovery steps share one cleanup
scope. If any later reconciliation fails after supervision started, the daemon
stops its threads and clears all in-memory supervision admissions before
propagating the error; a failed startup cannot leave renewable authority behind.

## 12. Configuration

Configuration is TOML with a required `schema_version = 1`. Unknown keys are
rejected recursively. It contains database, lease/retry defaults, partitions,
execution target references, execution profile names, adapters, and RootBridge.
Secrets and provider routing are referenced externally and never stored in Core
configuration.

An Execution profile registry supplied by the composition root is authoritative,
including when it is empty. A persisted profile absent from that registry is
`RESOURCE_UNAVAILABLE`; it must never silently fall back to adapter defaults.
`None` is reserved for direct callers that intentionally provide no registry.

Dynamic runtime state never writes back to configuration.

The daemon renews only Leases explicitly admitted by that daemon instance after
a bounded start or recovery observation positively identifies the exact
Execution as RUNNING. Database state and adapter registration do not create
admission. UNKNOWN/ambiguous observations revoke or withhold admission and do
not extend their deadline; the existing Lease remainder is their bounded
reconciliation grace. The positive RUNNING transition and first Lease renewal
commit in one fenced Core transaction before daemon admission, so a successful
start cannot lose authority in a confirm/heartbeat gap. On expiry, normal read-only/isolated recovery or writer
quiescence suspension applies. Strict validation
requires `dispatcher_poll_seconds <= heartbeat_seconds < lease_seconds`, so a
configured poll cadence cannot silently exceed the renewal safety window.
Core heartbeat and bulk renewal additionally require the persisted Execution
itself to be `RUNNING`; STARTING/UNKNOWN rows cannot be renewed even if a caller
incorrectly supplies their Attempt IDs.
`daemon --once` means one bounded run-to-idle cycle: after dispatch it keeps the
same process and adapter session alive until the current
STARTING/RUNNING/UNKNOWN Execution set is final. Its ceiling is the configured
`lease_seconds`; at the ceiling it invokes the existing terminate/cancel path
instead of orphaning a child or waiting forever. A writer whose quiescence is
still unknown remains subject to suspension/escalation. Long-running work uses
the normal resident `daemon`, not `--once`.
